## Тестовое задание на позицию Fullstack разработчика (Python + React)

**Вводные:**
1. Здесь представлен MVP проект файлообменника. Он позволяет загружать файлы, проверяет их на подозрительный контент и отправляет алерты;
2. Репозиторий содержит в себе бэкенд и фронтенд части;
3. В обоих частях присутствуют баги, неоптимизированный код, неудачные архитектурные решения.

**Задачи:**
1. Проведите рефакторинг бэкенда, не ломая бизнес-логики: предложите свое видение архитектуры и реализуйте его;
2. (Дополнительно) На бэкенде есть возможность неочевидной оптимизации - выполните ее;
3. (Дополнительно) Разбейте логику фронтенда на слои;

**Запуск:**
1. ```docker compose -f docker-compose.dev.yml up```
2. ```docker exec -it backend alembic upgrade head```


**Открыть фронт:** ```http://localhost:3000/test``` 

**Открыть бэк:** ```http://localhost:8000/docs```

**Консоль MinIO:** ```http://localhost:9011``` (minioadmin / minioadmin)

## Решение

### 1. Архитектура бэкенда

Исходный код держал подключение к БД, доступ к данным, бизнес-правила и HTTP-ошибки
в одном модуле `service.py`, а правила сканера были зашиты в тело Celery-задачи.
Разложено на слои с однонаправленными зависимостями `api → services → repositories → db`:

| Слой | Ответственность |
|---|---|
| `core/` | настройки (`pydantic-settings`) и доменные исключения |
| `db/` | один engine, одна фабрика сессий, `Base` |
| `domain/` | **чистые функции** без I/O: сканер, метаданные, решение по алерту |
| `storage/` | объектное хранилище за интерфейсом (`Protocol` + реализация на S3) |
| `repositories/` | весь SQL; транзакциями управляют сервисы, не репозитории |
| `services/` | оркестрация: валидация, хранилище, БД, вызовы `domain` |
| `api/` | тонкие роутеры, DI через `Depends`, маппинг ошибок в HTTP |
| `tasks/` | тонкие Celery-задачи, вызывают сервисы |

Ключевые следствия: `HTTPException` больше не проникает в бизнес-логику (сервисы кидают
доменные исключения, один обработчик переводит их в HTTP); наружу отдаются Pydantic-схемы,
а не detached ORM-объекты; engine создаётся один раз, а не отдельно в API и в воркере.

### 2. Неочевидная оптимизация

Обработка файла шла цепочкой из трёх Celery-задач (`scan → metadata → alert`), где каждая
задача сама ставила следующую через `.delay()`. На один файл это давало:

| | Было | Стало |
|---|---|---|
| Celery-задач (походов в брокер) | 3 | 1 |
| Сессий БД | 3 | 1 |
| `SELECT` одной и той же строки | 3 | 1 |
| `COMMIT` | 3 | 2 |

Причём шаг `scan` файл вообще не читал — он работал по полям, уже загруженным из БД,
то есть два из трёх походов в базу были чистыми накладными расходами.

Пайплайн схлопнут в одну задачу `process_file` (`services/processing.py`). Второй `COMMIT`
оставлен намеренно: ранний коммит фиксирует статус `processing`, иначе он не виден в UI
(в исходном коде статус выставлялся, но коммитился только в самом конце — вместе с
финальным результатом, поэтому пользователь его никогда не наблюдал).

Наблюдаемое поведение — значения статусов, тексты `scan_details`, уровни и тексты
алертов — сохранено дословно.

Сопутствующее: запись файла раньше выполнялась синхронным `write_bytes()` внутри
`async def`, то есть блокировала event loop на время записи. Теперь запись идёт через
асинхронный S3-клиент.

### 3. Хранилище

Файлы переехали из локальной папки контейнера в MinIO (S3-совместимое хранилище,
поднимается в compose). Доступ спрятан за интерфейсом `StorageBackend`, поэтому сервисы
не знают о S3. Бакет создаётся автоматически при старте приложения (FastAPI lifespan),
дополнительных шагов при запуске не требуется.

Загрузка и скачивание идут потоково: входящий файл считается чанками и уходит в
хранилище через `upload_fileobj`, ответ отдаётся `StreamingResponse` поверх `iter_chunks`.
Файл целиком в память не читается ни на одном из направлений. Проверено на 12 МБ.

### 3.1. Надёжность обработки

Задача `process_file` повторяется при транзиентных сбоях (недоступность БД или хранилища):
3 ретрая с экспоненциальной паузой. Статус `failed` и `critical`-алерт записываются только
на последней попытке — промежуточные сбои не плодят дубли алертов.

Прочее: `GET /health` проверяет БД и хранилище; в compose прописаны healthcheck'и, а
зависимости стартуют по `condition: service_healthy`; необработанные исключения логируются
и отдаются как 500 без утечки трейсбека; списки ограничены `list_limit`; бэкенд в контейнере
работает под непривилегированным пользователем.

### 4. Слои фронтенда

Страница на 367 строк, где были смешаны типы, запросы, состояние и разметка, разбита на:

```
lib/config.ts        базовый URL API (env вместо хардкода в трёх местах)
lib/api/             типизированный клиент: client, files, alerts
types/               FileItem, AlertItem
hooks/               useFiles (+поллинг), useAlerts, useUploadForm
components/          FilesTable, AlertsTable, UploadModal, badges, formatters
app/page.tsx         только композиция
```

### 5. Тесты

Unit-тесты на чистую логику — `backend/tests/` (сканер, метаданные, решение по алерту)
и `frontend/src/components/formatters.test.ts` (форматирование, вычисление статуса).
Слой, требующий БД/сети, тестами не покрывается сознательно.

```bash
docker run --rm -v "${PWD}/backend:/w" -w /w ghcr.io/astral-sh/uv:python3.14-bookworm-slim uv run --group dev pytest
```
```bash
cd frontend && npm test
```

Линтер бэкенда (ruff):

```bash
docker run --rm -v "${PWD}/backend:/w" -w /w ghcr.io/astral-sh/uv:python3.14-bookworm-slim uv run --group dev ruff check .
```

### 6. Исправленные баги

1. `DELETE /files/{id}` возвращал 500 и **безвозвратно терял файл**: объект удалялся с диска
   до записи в БД, а `commit` падал на внешнем ключе из `alerts`. Теперь алерты и файл
   удаляются в одной транзакции, а хранилище трогается только после успешного коммита.
2. Сборка фронта падала: `Dockerfile` копировал несуществующий `.env.production`.
3. Несовместимость версий: React 18 в лок-файле против Next 16.
4. `backend` и `backend-worker` не зависели от `backend-redis` в compose.
5. Статус `processing` не был виден из-за единственного коммита в конце обработки.
6. Падение любой задачи молча обрывало цепочку — файл навсегда оставался в статусе
   `uploaded`. Теперь сбой фиксируется как `failed` с `critical`-алертом.
7. Отсутствовал лимит размера загрузки — файл любого размера читался в память целиком.
8. Расхождение имён переменных: код читал `REDIS_URL`, окружение задавало `CELERY_BROKER_URL`.
9. `favicon` запрашивался по пути `/public/favicon.ico`.
10. Фронт не обновлял статусы после загрузки — только по кнопке «Обновить».
